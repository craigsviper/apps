## ⚠️ MANDATORY: any new app field/collection must also be wired into the host-server's sync merge

**If you add a new field to any record, or a new collection to `AppData`, the host-server's `mergeData()` in `server.js` must be updated in the same change — not as a follow-up.** This project's own history (see Recent History below: v71.x's `pushToServer()` regression, v73.4/v73.5's `tipRuns`/`extraExpenses`/`inspections` photo-merge gaps, v72.2's `maps.pins`) is a long list of exactly this mistake: a field or nested array gets added or edited on the app side, nothing on the server side knows to merge it by id instead of doing a whole-record overwrite, and it gets **silently dropped** the next time two devices sync — no error, no warning, just quietly missing data days or weeks later when someone notices.

Concretely, for any app-side change, check:
- **New top-level collection added to `AppData`?** Add it to `ALL_INSPECTION_KEYS`/`ALL_SWEEP_KEYS` (app) AND to `ALL_COLLECTIONS` + `mergeData()`'s per-collection branches (server) AND `mergeServerDataIntoLocal()` (app's own push/pull merge helper) — the "unknown key" fallback paths on both sides will technically keep it alive, but only with a generic whole-record merge, which is exactly the gap that's bitten this project repeatedly.
- **New field on an existing record?** If it's a plain scalar (string/number/boolean), a whole-record field-union merge already covers it for free — no server change needed. If it's a **nested array** (like `photos`, `pins`, `roads`, `tipRuns`, `segmentSettings`) or a **nested id-referencing array**, it needs its own id-based union merge on the server, the same class of fix as `mergeSweepJobs`/`mergeInspections`/etc. already have — a naive whole-record merge will let one device's edit silently overwrite another device's on that nested array.
- **When in doubt, grep `mergeData()` in `server.js` for the collection you're touching and check whether nested arrays inside it are already covered by name**, rather than assuming "it's just one more field, it'll be fine."

This is not optional cleanup — it's the difference between "sync merges your data" and "sync silently deletes your data whenever two people happen to edit around the same time," which is the single most-reported category of bug in this project's history.

## What This App Is

**RSW Field App** — a Progressive Web App (PWA) for road sweeping crews and site inspection teams working in the field. Built with React + TypeScript + Vite, served as a **single inlined HTML file** (via `vite-plugin-singlefile`). All data is stored locally in **IndexedDB** and optionally synced to a self-hosted **Node.js/Express sync server** running in Docker.

Primary field device: **Firefox on Android** (offline mode). The app must work fully without internet.

### Select Roads Strict-mode traversal — known limitations (v73.111–v73.117)

`traverseSelectedGraphOrdered()` in `SweepJobs.tsx` (~line 1613) is a **shortest-path/full-coverage graph walk, not a provably-optimal route inspection (Chinese Postman) solver.** Read this before re-diagnosing a "traversal distance/behaviour looks wrong" report from scratch:

- **A≠B routes:** point-to-point Dijkstra + a reuse penalty. Not guaranteed globally minimal on a graph with many alternate cycles, but verified never to repeat an edge without a real reason (dead-end or turnaround).
- **A=B routes (closed loop):** `traverseLoopCoverage()` — a DFS spanning-tree walk of the whole connected selected-road graph.
  - One cycle-*closing* edge (where the loop rejoins itself) can be traversed twice instead of the theoretical minimum of once — a single extra edge-length, bounded, not the exponential same-branch-repeated-many-times bug v73.112→v73.113 fixed.
  - **v73.117: turnaround markers are now mandatory stop-and-reverse points, even at a real connected junction with a through option** — not just true dead-ends. Craig's real case: T3 sits where Moa Crescent meets Weka Street, a genuine drivable connection, but he needs the truck to stop and reverse there anyway rather than flow through. `traverseLoopCoverage()` takes a `turnaroundNodeKeys` set; arriving at one of those nodes via any edge forbids exploring its other edges on that visit — it backtracks immediately. Whatever lies beyond (e.g. Weka Street itself) still gets swept, just reached later from its other end. Before v73.117, turnaround markers were ignored entirely in loop mode on the (wrong, for connected junctions) assumption that full coverage already reaches everywhere a marker would matter.

Fully closing the A≠B/A=B optimality gap above needs real Eulerian-circuit/minimum-weight-matching logic across odd-degree nodes — out of scope so far, flagged consistently since v73.111. The turnaround-at-junction gap (previous bullet) is now fixed as of v73.117, not open.

Every Strict-mode "Add to Segment" logs `[traverseSelectedGraphOrdered] total=...km unique=...km turnaround-return=...km other-repeated=...km` to the console (v73.112+), with a `console.table` of specific offending edges if `other-repeated` exceeds ~1m. **Read that log before re-diagnosing a "too much distance" report** — `other-repeated` near 0 means the algorithm is working as designed (the bounded gaps above), not a new bug.

## Data Model

All data lives in a single `AppData` object — 16 array collections persisted to IndexedDB and synced as one JSON payload.

```typescript
interface AppData {
  users:           User[];
  clients:         Client[];
  inspections:     Inspection[];
  maps:            InspectionMap[];
  categories:      Category[];
  reports:         Report[];
  coverTemplates:  CoverTemplate[];
  sweepAreas:      SweepArea[];
  sweepRoads:      SweepRoad[];
  sweepJobs:       SweepJob[];
  sweepClients:    SweepClient[];
  sweepJobSites:   SweepJobSite[];
  sweepFiles:      SweepFile[];
  sweepCategories: SweepCategory[];
  sweepMaps:       SweepMap[];       // auto-generated, read-only in UI
  sweepReports:    SweepReport[];    // auto-generated, read-only in UI
}
```

In `src/store.tsx` these 16 keys are assembled from two arrays — `ALL_INSPECTION_KEYS` and `ALL_SWEEP_KEYS` — concatenated into `ALL_KEYS`. When adding a 17th collection, add it to whichever of those two arrays fits, AND to `mergeServerDataIntoLocal()`'s explicit per-collection merge calls, AND to `MERGE_KNOWN_KEYS` — the "unknown key" fallback path will keep it working without those, but only with a generic (non-nested-field-aware) merge.

### SweepCategory structure

Each `SweepCategory` record is a **named list** of items belonging to a `categoryType`:

```typescript
interface SweepCategory {
  id: string;
  name: string;          // list name, e.g. "Sweeper drivers"
  categoryType: string;  // e.g. "crew_member", "debris_type", "weather"
  items: { name: string; color: string; description: string }[];
  createdAt: string;
  updatedAt: string;
}
```

Known `categoryType` values: `damage_type`, `damage_severity`, `debris_type`, `debris_level`, `zone_type`, `frequency`, `crew_member`, `equipment`, `pass_count`, `site_type`, `file_attachment`, `weather`, `extra_expense`, `job_site_map_pin`, `custom`.

`consolidateSweepCategories()` / `consolidateCategories()` (module-level functions in `store.tsx`) repair duplicate/empty-husk category lists left behind by old app builds — run automatically on every Push and every Pull. As of v71.8, the 14 (or 3) built-in list ids can no longer be deleted server-side either (`SW_CAT_ID_TO_TYPE`/`CAT_ID_TO_TYPE` guard in `server.js`).

## Sync / Persistence Rules

**Read carefully before touching sync code — this area has regressed once already (see the warning banner at the top of this file).**

- **IndexedDB** is the source of truth on the client. Every `setData()` call auto-saves via a `useEffect` in `store.tsx` (`useEffect(() => { if (dbReady) saveData(data); }, [data, dbReady])`).
- `exportData()` — serialises all 16 collections to JSON string.
- `importData()` — full restore; spreads unknown future array keys for forward-compat (see `KNOWN_KEYS` set in `store.tsx`).
- `pushToServer()` / `pullFromServer()` — **live in `src/store.tsx`** (not `Backup.tsx` — `Backup.tsx` only calls them and renders the UI/dialogs around them).
- **Merge strategy is purely additive, in both directions — there is no auto-delete propagation.** A shared module-level helper, `mergeServerDataIntoLocal()` (built from `mergeArrays`/`mergeCategories`/`mergeInspections`/`mergeMaps`/`mergeSweepJobs`/`mergeSweepJobSites`/`mergeRecord`/`unionById`/`unionStrings`), is used by BOTH `pushToServer()` and `pullFromServer()` so a sync in either direction can only add/update local or server data — it can never make a record disappear on its own. **This was implemented once, then regressed (push silently went back to a raw `merged[k] = raw[k]` overwrite) when the file got ported across a divergent branch, and was re-fixed in v71.9.** If you ever see `pushToServer()` or `pullFromServer()` NOT calling `mergeServerDataIntoLocal()`, that's a regression — fix it the same way again.
- **Deleting something is always a manual, one-side action** (v71.5+). Deleting a record in the app removes it from the app only. Deleting a record on the host-server (dashboard) removes it from the server only. Neither side auto-propagates a delete to the other during sync — this replaced the old tombstone-based auto-delete system.
  - Server-side: `POST /sync` no longer calls a tombstone-stripping step before merging a push, so pushing a record the device still has will restore it to the server even if it was deleted there (this is the intended "undo").
  - Client-side: `pullFromServer()` tracks which record ids were confirmed present on the server as of the last sync (`rsw_known_server_ids` in `localStorage`, via `loadKnownServerIds()`/`saveKnownServerIds()`). If a local record's id was previously confirmed on the server but is missing from the latest pull, it's added to `pendingServerDeletions` (context state) and `Backup.tsx` shows a review dialog: **Keep** (do nothing locally — next Push & Sync restores it on the server) or **Delete** (removes it locally too, via `resolveServerDeletions()`). Brand-new local records never pushed yet are never flagged, since they were never in the "known server ids" set.
  - The host-server's own tombstone bookkeeping (`addTombstone`, `pruneTombstones`, `/tombstones` GET/remove/prune endpoints, the dashboard's Health-page Tombstones card) still exists — that's the dashboard operator's own manual recently-deleted/restore + age-based bulk-cleanup tool, unrelated to (and no longer wired into) the sync merge path.
- Unknown/future array keys in a server response are still preserved (not dropped) by both push and pull, via the `MERGE_KNOWN_KEYS`-guarded loop inside `mergeServerDataIntoLocal()` (plus a `_legacy` prefix exclusion) — so a newly added 17th collection doesn't strictly need code changes to survive a sync, though it should still be added properly (see Data Model section above) for a collection-aware merge rather than the generic fallback.
- **Server-side `mergeData()` (`server.js`) has its own separate set of nested-array merge branches — don't assume client-side additive-merge safety (above) automatically covers the server.** `categories`/`sweepCategories` get item-level merge (`mergeCategoryItems`), `sweepJobs` gets a deep merge of `roads` (by `roadId`, and — as of **v73.9** — `damagePins`/`segmentSettings` *within* each road too, by id and by `segIdx` respectively), `fuelDockets`, `extraExpenses`, and (as of **v73.4**) `tipRuns` (by run id, then by trip id within each run — two levels deep), and (as of **v72.2**) `maps` gets an id-based union of `pins`, and (as of **v73.5**) `sweepMaps`/`inspections`/`sweepJobSites` get the same id-based sub-array treatment, and (as of **v73.9**) `sweepRoads.segments` gets the same treatment too (client-side `mergeSweepRoads()` landed in **v73.10** — see the note below), plus several collections gained plain id-reference-array unioning (`reports.inspectionIds`/`categories`, `sweepReports.jobIds`/`areaIds`, `sweepAreas.roadIds`, `sweepJobs.areaIds`/`fileIds`) — all other collections still go through the generic whole-record `mergeArrays()`, which is a field-union *at the record level only* and will silently overwrite any nested array field wholesale if you add a new collection with nested array data without a dedicated branch. This was exactly the `maps.pins` bug fixed in v72.2 (pins added on one device vanished if another device's edit to the same map record won on `updatedAt`) and the `sweepJobs.tipRuns` bug fixed in v73.4 (same thing, discovered by checking Craig's "will it drop it" question rather than assuming a new field on an already-deep-merged parent record was automatically safe) — if a future collection or nested field has its own per-item ids, give it the same treatment, don't rely on the generic branch or assume a sibling field being merged means all fields are. **The client side (`store.tsx`'s `mergeServerDataIntoLocal()`) needs the exact same coverage, separately — it is NOT automatically kept in sync with server.js.** This was learned the hard way in **v73.10**: a session fixed `sweepJobs.roads[].segmentSettings` server-side (v73.9) but never mirrored it to `store.tsx`; a *different, sibling* session independently found and fixed `sweepRoads.segments` on both sides in its own v73.9. Reconciling the two uploaded zips into one (v73.10) is what caught the missed client-side `segmentSettings` piece — neither session alone would have found it. Always check and fix *both* files together, never just one, and when reconciling two sessions' parallel work, diff what each one touched rather than assuming "same version number" means "same changes." **Known, deliberate gap (checked in v73.5, not fixed):** `sweepRoads.points`/`.segments[].points` (route geometry) are NOT deep-merged — `RoadPoint` has no `id` field (just `lat`/`lng`/`transitAfter`), so there's no safe identity to merge by; merging by array index would misalign and corrupt the route if the two devices' point arrays differ in length, which is worse than the current whole-record behavior. Redrawing a route is realistically a single-device operation anyway (lower real-world concurrent-edit risk than photos/pins/trips). If this ever needs revisiting, it would need a different approach (e.g. giving points stable ids), not a naive extension of the pattern used elsewhere in this function.

### On-device Debug Log (`src/logger.ts`, v71.8–v71.9)

- Day-rotated JSON arrays in `localStorage` (`rsw_log_YYYY-MM-DD`), retention-pruned to a configurable number of days (default 4, `rsw_log_retention_days`), capped per-day at 1000 entries.
- `LogType`: `'push' | 'pull' | 'sync-error' | 'add' | 'update' | 'delete' | 'info' | 'error'`.
- **v71.9: a single diff-based `useEffect` in `store.tsx`** (compares `data` before/after on every change, per collection, per record id) is what actually populates `'add'`/`'update'`/`'delete'` entries — NOT individual CRUD functions. This catches every mutation path (manual edit, import/restore, sync merge) automatically; don't add per-function `logEvent()` calls for CRUD, the diff effect already covers it. `'error'` entries come from global `window.onerror`/`unhandledrejection` listeners, also in `store.tsx`. `'push'`/`'pull'`/`'sync-error'` remain explicit calls inside `pushToServer()`/`pullFromServer()`.

## Server Dashboard Notes

- The dashboard UI is entirely inline in `server.js` as template literal strings inside `res.send(...)`.
- **Nested template literals inside `res.send()` MUST escape backticks as `` \` `` and `${` as `\${`** — this is a recurring source of syntax errors. **The same applies to any escape sequence meant for the browser's own JS string literals — `\n`, `\t`, `\\`, etc. — write `\\n` (not `\n`) so the server's template-literal parsing leaves a literal `\n` in the emitted string for the browser to interpret. A plain `\n` gets consumed at the server level and becomes a real newline byte sitting inside the browser's string literal — an unterminated string, which is a hard syntax error that kills the ENTIRE dashboard `<script>` block, not just the one feature (this happened for real in v73.0, hotfixed in v73.1).**
- **Verification rule (added after v73.0/v73.1): `node --check server.js` only validates server.js's own syntax — it cannot see inside the strings server.js emits, so it will NOT catch a broken escape sequence like the one above. Before considering any dashboard-JS change verified, boot the server, fetch the actual rendered `/dashboard` response, extract the `<script>` content, and run `node --check` on THAT. Better still, load it in a real headless browser (Playwright, if available) and confirm zero console/page errors.**
- `renderSweepCategories()` — custom grouped view; supports per-item delete (`deleteSwCatItem`) and per-item add (`addSwCatItem`) using PUT `/data/sweepCategories/:id`.
- `api(path, opts)` — dashboard fetch helper; throws on non-ok responses and returns parsed JSON directly (do NOT check `.ok` on the result).
- Generic `DELETE /data/:collection/:id` and the "Delete ALL records in <collection>" dashboard button already cover manual delete for all 16 collections — no per-collection delete endpoints needed if a 17th collection is added. Built-in `sweepCategories`/`categories` list ids are protected from deletion (v71.8) via `SW_CAT_ID_TO_TYPE`/`CAT_ID_TO_TYPE`.
- The dashboard's own "Auto Delete" setting (`config.autoDelete`, `keepLastNAutoDelete`, `deleteDays`) prunes old **backup ZIP files**, not data records — do not confuse this with the (removed) data auto-delete/tombstone sync propagation described above, or with the Tombstones-panel age-based **prune** (`POST /tombstones/prune`, v71.8) which deletes old tombstone bookkeeping entries, not backups. Three similarly-named but distinct "delete old stuff" features exist; check which one before changing any of them.
- **Debug page** (v71.8) — `console.log`/`warn`/`error` wrapped at startup to capture everything to `DATA_DIR/logs/YYYY-MM-DD.log`. Routes: `GET /logs`, `GET /logs/today/live` (v73.0 — todays raw text for the auto-refreshing Live panel, keyed off the servers own todayStr()), `GET /logs/:date`, `DELETE /logs/:date`, `DELETE /logs`. Retention via `logRetentionDays` setting (default 4), auto-prunes on settings save and startup. This is the server-side counterpart to the app's own Debug Log (see Sync/Persistence Rules above) — the two are entirely separate log stores (one per device/browser, one on the server) and are not synced or merged with each other.

## Firefox Android / Offline Notes

- App is a `vite-plugin-singlefile` build — all JS/CSS inlined in `index.html`. Service worker caches `index.html` = caches entire app.
- `sw.js` CACHE_NAME must be bumped on every release to bust the old cache and serve the updated app.

- Firefox on **iOS** is WebKit under the hood — aggressive cache eviction applies. Not fixable in code.
